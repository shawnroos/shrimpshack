### R1 — P2 — RESOLVED in c8c5f00 — the TodoWrite matcher could not fire in agent/SDK/team sessions
`plugins/reflect/.claude/hooks/hooks.json`

`TodoWrite` and `TaskCreate` both exist in build 2.1.226, and which set a session
exposes varies by session shape. Agent/SDK/team sessions expose
`TaskCreate`/`TaskUpdate`/`TaskList` and **no `TodoWrite`** — the session that built
this branch is one of them. So U0 restores the all-todos-done trigger for
interactive sessions only, and the plan's own build sessions are among those where
it cannot fire.

**Resolved.** A `TaskUpdate` matcher was added, gated on `status == "completed"`.
Deliberately a different signal rather than a port: TodoWrite carries the whole list
so "all done" is answerable from one payload, while TaskUpdate carries one task and
cannot answer it. So it fires per completion and relies on `reflect-trigger.sh`'s
existing 600s coalesce window, and writes its own reason string so REFLECT.log shows
which signal fired. Load-bearing: dropping the status gate fails the silence
assertion.

### R3 — P3 — RESOLVED in 949b3a8 — `repo_root` was wrong for submodules
`plugins/reflect/scripts/scoped-memory/scope.py:52-66`

Demonstrated on a real submodule: a submodule's `.git` is a **file** pointing at
`<super>/.git/modules/<name>`. That path ends in neither `/.git` nor a `.git`
basename, so both fold branches fall through and the resulting scope slug names a
path **inside** `.git` — neither the submodule checkout nor the superproject.

```
/…/sm/super/sub -> repo_root= /…/sm/super/.git/modules/sub
                   slug= …-sm-super-.git-modules-sub
```

**Resolved.** A submodule's common-dir now folds to the superproject. The assertion builds a real submodule rather than mocking one, since the whole bug is in what git actually reports; removing the fold returns `.../super/.git/modules/sub` and fails it.

Was pre-existing and unrelated to this branch.
Note separately that reverting the `--show-toplevel` change earlier in this branch
was still **correct** — that change broke the worktree→parent fold, which is a
different and much more common case.

### R4 — P3 — RESOLVED in 13119a8 — one harness block depended on globally-stateful qmd
`plugins/reflect/tests/harness.sh` (qmd reconcile block)

Mitigated in `8286190` but not eliminated. qmd's collection state is **global** on

**Downgraded to P3, with the reasoning stated rather than assumed.** It was P2

### X1 — P1 — RESOLVED in 0ffb3e7 (store owner's call): the floor was dead on a small store
`plugins/reflect/scripts/scoped-memory/local_index.py`

The 12.0 absolute floor was calibrated on 886 bodies. BM25 sums IDF terms and IDF
grows with log(N), so the constant does not transfer to a small corpus. Measured by
building fixture stores and running the real code:

```
N= 3  pre-fix=below_gate  top=5.63     <- a true hit, refused
N= 5  pre-fix=below_gate  top=7.30     <- a true hit, refused
N= 8  pre-fix=below_gate  top=8.91     <- a true hit, refused
N=12  pre-fix=below_gate  top=10.41    <- a true hit, refused
N=20  pre-fix=hits        top=12.61
```

So below roughly 20 memories the local fallback silently returns nothing, however
good the match — which is precisely a fresh install, the case with no telemetry to
notice.

**Resolved: adaptive floor with a hard guard, chosen by the store owner.**
`floor_for_corpus` scales by `log1p(N)/log1p(886)` — exactly 12.0 at the calibration
size and above, never scaled up, and never below a guard that stops it collapsing on
a near-empty store.

The honest limit is written into the module rather than glossed: on a small corpus
the true and junk bands OVERLAP (N=8: true 8.52 vs junk 7.84; N=20: 11.39 vs 10.84),
so no absolute floor separates them and the ratio does not rescue it. Small-store
recall is weaker, not merely rescaled. The guard is provisional — picked from
synthetic fixtures, since no real small store exists to measure — and RECALL.log now
records the scores needed to replace it.

Original analysis follows, kept because it is the evidence for the decision:

**A scaling fix was written, verified, and then reverted once before this.** Scaling the floor by
`log1p(N)/log1p(886)` preserved the calibration exactly at N>=886 and made the
small-store true hits pass. It also broke three existing assertions — junk queries
that a small fixture used to reject now cleared the lowered floor. That is not a
test problem; it is the actual tradeoff surfacing. On a small store the choice is
**no recall at all** versus **recall with weaker precision**, and the plan's settled
principle is explicit: *a wrong memory costs more than no memory.* Changing that
balance is a product decision, not an implementation detail, so it is recorded here
rather than decided unilaterally.

Options if it is taken up: scale the floor and accept looser precision on small
stores; keep 12.0 and document that the local layer needs ~20 memories before it
contributes; or make the floor adaptive with a hard minimum so it can loosen but
not collapse.

### X2 — P2 — RESOLVED in c8c5f00 — the contract overclaimed for singletons
One candidate above the floor passes on the floor alone, since no top1/top2 ratio
exists. That is the specified behavior, but the module's claim that it "never
returns a flat guess" is not true of that path — a lone lexical match is exactly a
flat guess. **Resolved by scoping the claim** to the ranked path, with the reason singletons
are still admitted: refusing every singleton would make a sparse or heavily-filtered
corpus permanently silent. Behavior unchanged; the claim now matches it.

### X3 — P2 — RESOLVED in c8c5f00 — the stated pipeline order did not match the code
The docstring says siblings are dropped first, then scoring. In fact `score_all()`
scores every matching body including siblings, and `scope.classify` filters
afterwards. No verdict is wrong today — sibling scores never enter `above` or the
ratio — but the ordering claim was inaccurate. **Resolved in the docstring**,
which now states that scoring happens first and filtering immediately after, and
that the numbered order is about which scores the GATE reads rather than which
bodies get scored.

### X4 — P3 — refuted by measurement: env config validation
The reviewer expected an unvalidated `MEMORY_LOCAL_FLOOR_MIN` to be able to disable

## X8 — P1 — the confidence gate refuses half of its true hits

**Found by pulling on X1 instead of accepting the patch.** X1 was "the floor is
miscalibrated for small stores", and the fix was to rescale the floor. That is polish
on a design that is wrong at the root, and the code said so itself: *"a floor is a
property OF A CORPUS."* A gate needing recalibration whenever the data changes is
fragile by construction — raw BM25 score is not a portable unit for "is this good
enough".

Measured on the LIVE store (889 bodies), four queries whose answers are definitely on
disk, run through the SHIPPED gate:

```
hits         failing E2E shard sprout spec flake...   floor cleared; separation 1.70 >= 1.40
hits         PR conflicting stopped running CI...     floor cleared; separation 1.44 >= 1.40
below_gate   seeded recall hook taxes every prompt... separation 1.07 below 1.40
below_gate   agent browser cannot send modifier keys  separation 1.13 below 1.40
```

**Two of four true hits are refused** — and refused by SEPARATION, not the floor.
That is the exact failure this plugin exists to remove: a memory that is present,
correct, and never surfaced. The 1.40 threshold rests on three data points, which the
plan states plainly at the definition site.

The runner-up in both refusals is a genuinely related memory. The gate reads "two
things match" as "I cannot tell" and returns nothing — when the honest answer is two
candidates and one extra line of output.

### The scale-free alternative, measured

Coverage — what fraction of the query's own meaningful terms the top hit actually
contains — separates cleanly where raw score does not, and never needs recalibrating
because it is measured against the query rather than the corpus:

```
        query                                      top    ratio   COVER
TRUE    failing E2E shard sprout spec flake...    41.73    1.70    1.00
TRUE    seeded recall hook taxes every prompt...  33.85    1.07    0.88
TRUE    agent browser cannot send modifier keys   21.07    1.13    0.83
TRUE    PR conflicting stopped running CI...      27.88    1.44    0.75
JUNK    statusCheckRollup CodeRabbit SUCCESS       7.50    1.01    0.67
JUNK    completely unrelated gardening tulips...  10.10    1.62    0.40
JUNK    capital city of france population          5.95    1.03    0.25
JUNK    xyzzy plugh frobnicate quux                0.00    0.00    0.00
```

True 0.75–1.00, junk 0.00–0.67. The bands separate at ~0.70. Note the gardening
query: ratio **1.62** would have PASSED the current separation gate, and only
coverage catches it — so the current design is wrong in both directions.

A prototype (coverage >= 0.70 gating relevance; a thin margin returning BOTH
candidates with a note rather than returning nothing) scored **8/8** on that set: all
four true hits returned, all four junk queries refused.

### Why it is not applied here

The prototype works, but landing it invalidates ~40 lines of `local_index_test.py`
built specifically to prove the FLOOR is load-bearing — including the arithmetic
demonstration against `recall_floor` that KTD12 rests on. Replacing that with
equivalent fixture evidence for coverage is real work, and a hurried rewrite of the
tests that justify a gate is precisely how a false green is manufactured. This same
session already caught four false-positive assertions written in haste.

The diagnosis is high-confidence and measured; the cure deserves its own pass with
proper fixture work. Prototype and measurements are reproducible from this file.

**Until then the shipped gate is too strict**, and the practical mitigation is
`--deliberate`, which relaxes it — which is what `/memories` and `/reflect regroup`
already pass.
