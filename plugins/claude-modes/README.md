# claude-modes

A modal harness for Claude Code. Named, durable, mutually-exclusive
working stances that reshape the plugin layer at the harness level so
the model context is **modal**, not flat. Stop carrying every plugin
into every session; let the active mode pick.

`/mode:set delivery` swaps the plugin loadout. `/mode:set discovery`
swaps it back. The mode persists across restarts, follows your branch,
and (V2) cascades through five tiers of configuration so machine-wide,
mode-specific, and repo-specific decisions all compose into the same
final answer.

> **V2.0 scope.** V2 ships the cascade architecture and per-repo
> isolation, but the cascade payload is limited to `enabledPlugins`
> only — the one key Claude Code's `/reload-plugins` actually
> hot-reloads in-session. Hooks, env vars, permissions, and non-plugin
> MCP servers stay in `~/.claude/settings.json`, user-managed. See
> [Known limitations](#known-limitations).

---

## Install

From inside Claude Code, run:

```
/mode:setup
```

`/mode:setup` moves your existing `~/.claude/commands/*` and
`~/.claude/agents/*` into a staging directory under
`~/.claude/modes/_user_catalog/`, symlinks them back so nothing breaks
today, generates `~/.claude/modes/_global.yaml` from your current
`enabledPlugins`, snapshots `~/.claude/settings.json` to
`~/.claude/settings.json.pristine` as a forensic anchor, and seeds an
install registry. It is idempotent — re-running is a no-op.

The plugin itself lives at `~/.claude/plugins/claude-modes/` (or as a
symlink to your dev checkout). It is installed via Claude Code's
plugin marketplace mechanism; `/mode:setup` is the post-install step
that prepares your user catalog and per-machine baseline.

## Use

```
/mode:set delivery              # activate the delivery mode
/mode:clear                     # return to Claude Mode (no mode active)
/mode:status                    # show active mode + visible cascade tiers
/mode:registry                  # list all modes globally available
/mode:adopt <command|agent>     # add a user-catalog file to the active mode
/mode:statusline install        # wire mode visibility into your statusline
```

Modes are **per-branch** by design: `feature/ai-pipeline` and
`main` can have different active modes in the same repo, and a
worktree carries its own pointer. `/mode:set` writes a pointer
file to `<repo>/.claude/modes/<branch-slug>.mode` and triggers
`/reload-plugins` so the new loadout takes effect without a session
restart.

## How modes work (the cascade)

V2 evaluates five configuration tiers and merges them into a single
`enabledPlugins` map written to `<repo>/.claude/settings.local.json`.
Tier 5 is reserved for future use; the active four are:

```
Tier 1 (always)   ~/.claude/settings.json               # user-managed; cascade DOES NOT WRITE
Tier 2 (always)   ~/.claude/modes/_global.yaml          # machine-wide baseline (R22 — always claude-modes)
Tier 3 (mode set) ~/.claude/modes/<mode>.yaml           # the active mode's overlay
Tier 4 (in repo)  <repo>/.claude/modes/_repo.yaml       # repo-wide baseline (optional)
Tier 6 (pointer)  <repo>/.claude/modes/<slug>.mode      # selects which mode is active
```

Merge semantics: additive by default (`true` wins over `false`); the
`disable:` block subtracts. A higher tier can subtract a plugin
enabled in a lower tier by name; everything else accumulates.

### Worked example

**`~/.claude/modes/_global.yaml`** — generated by `/mode:setup`,
edited by hand thereafter:

```yaml
schema_version: 2
name: _global
mechanism:
  enabledPlugins:
    "claude-modes@local-dev": true            # R22 invariant
    "compound-engineering@every-marketplace": true
```

**`~/.claude/modes/delivery.yaml`** — the active mode (tier 3):

```yaml
schema_version: 2
name: delivery
mechanism:
  enabledPlugins:
    "slate-devs@local": true                  # delivery-specific reviewer
disable:                                       # TOP-LEVEL key, sibling of mechanism:
  enabledPlugins:
    - "rapid-prototyper@marketplace"           # subtract from cascade
```

**`<repo>/.claude/modes/_repo.yaml`** — repo baseline (tier 4),
optional:

```yaml
schema_version: 2
name: _repo
mechanism:
  enabledPlugins:
    "this-repo-codegen@private": true
```

Cascade result written to `<repo>/.claude/settings.local.json`:

```json
{
  "enabledPlugins": {
    "claude-modes@local-dev": true,
    "compound-engineering@every-marketplace": true,
    "slate-devs@local": true,
    "this-repo-codegen@private": true
  }
}
```

`/reload-plugins` consumes the new `settings.local.json` and the
running session picks up the new loadout. No restart needed.

**Honest constraint:** only `enabledPlugins` flows. If your mode wants
mode-specific hooks, env vars, or permissions, those live in
`~/.claude/settings.json` directly (user-managed) and require a
restart to change. See [Known limitations](#known-limitations).

## How V2 handles your files

The plugin's R19 invariant: **never silently mutate the user's
catalog.** Specifically:

- The plugin **never** writes to `~/.claude/settings.json`. It writes
  `~/.claude/settings.json.pristine` (a one-time forensic snapshot)
  and `<repo>/.claude/settings.local.json` (per-repo cascade output).
  Your settings.json stays as you authored it.
- User commands and agents at `~/.claude/commands/*` and
  `~/.claude/agents/*` are **moved** to staging at
  `~/.claude/modes/_user_catalog/`, then **symlinked back**. Your
  existing tools keep working. Per-mode user-catalog selection is
  done by rebuilding the symlinks during `/mode:set`.
- Every settings-derived file the plugin owns is **born at mode
  0600**. Includes `_global.yaml`, `settings.json.pristine`,
  `.installed-repos.txt`, `.trusted-repos.txt`, `.audit.log`, per-repo
  `settings.local.json`, and the sidecar `.cascade-meta.json`.
- The cascade output's sidecar (`.cascade-meta.json`) records the
  content hash of `settings.local.json` so uninstall can tell whether
  you (or another tool) edited it post-cascade. Pattern adopted from
  direnv's `.envrc` allow mechanism.
- Foreign `_repo.yaml` files (cloned from someone else's repo) hit
  the **trusted-repos.txt consent gate** on first `/mode:set`. The
  cascade engine surfaces a named diff of what the file would add to
  your loadout; you trust by repo path. Re-edits re-prompt by
  content hash.

The `.installed-repos.txt` registry is append-only at write, set-
deduped on read. Uninstall iterates that registry and cleans up each
repo it touched — including repos you've since deleted (those
silently no-op) and repos that have moved (those surface a warning).

## Uninstalling

```bash
bash ~/.claude/plugins/claude-modes/scripts/unmodes.sh
```

Walks the install registry; for each listed repo, removes
`<repo>/.claude/settings.local.json` **only if** its content hash
matches the sidecar's `fingerprint` (plugin-authored and unedited).
If you (or another plugin) edited the file post-cascade, the hash
mismatches and uninstall preserves your local edits, deletes only the
sidecar, and surfaces a "review and clean up manually" message.

Uninstall also:

- Moves user-catalog files back from `~/.claude/modes/_user_catalog/`
  to `~/.claude/commands/` and `~/.claude/agents/` (symmetric to
  `/mode:setup`).
- Deletes `~/.claude/modes/`.
- **Does NOT touch** `~/.claude/settings.json`. The plugin never owned
  it; uninstall never restores from `settings.json.pristine`. If you
  want the pristine snapshot gone, `rm ~/.claude/settings.json.pristine`
  after uninstall completes.

## Security model

Three layers, each with a regression test:

1. **R7 — Path-traversal in user-catalog symlinks.** When `/mode:set`
   rebuilds symlinks from `_user_catalog/` into `~/.claude/commands/`
   and `~/.claude/agents/`, every link target is `realpath`-resolved
   and checked to be a child of the staging directory. A
   symlink-with-shaped-name pointing at `/etc/shadow` is rejected
   before write. Test: `tests/integration/symlink-path-traversal.test.sh`.
2. **R28 — Hooks forbidden in mode YAMLs.** Mode YAMLs (tier 3) and
   `_repo.yaml` (tier 4) MUST NOT declare hooks. The cascade engine
   asserts this at parse time. Reason: hooks live at the
   `~/.claude/settings.json` level and require a session restart to
   change — putting them in a cascade tier would create a misleading
   user contract. Test:
   `tests/integration/r28-hooks-forbidden-in-mode.test.sh`.
3. **R24 — 0600 file permissions.** Every settings-derived file the
   plugin creates is born at mode 0600 atomically (via `os.open(...,
   0o600)` + `os.replace`, not chmod-after-write). Test:
   `tests/integration/settings-file-perms.test.sh`.

The trusted-repos consent gate adds a fourth layer for foreign
`_repo.yaml` content. The gate is narrowed to `enabledPlugins`
changes only (matching the V2 scope cut): cosmetic changes don't
re-prompt; effective changes always do.

## Known limitations

V2.0 scope cuts (deferred to V2.0.1+ or V2.1):

- **Mode-scoped hooks** — hooks live in `~/.claude/settings.json`. To
  change them per mode you'd need a new session per swap; not worth
  the misleading UX. Edit `~/.claude/settings.json` directly.
- **Mode-scoped env vars** — process environment is captured at
  startup; architecturally not hot-reloadable.
- **Mode-scoped permissions** — `/reload-plugins` does not reload
  permissions per the binary verification of Claude Code 2.1.143.
- **Mode-scoped non-plugin MCP servers** — non-plugin MCP servers
  require a new session.
- **Permissions diff/confirm gate** — moot, since permissions aren't
  in the cascade.

**Secrets in `_repo.yaml`.** Because `_repo.yaml` lives in your repo,
committing it shares its `enabledPlugins` decisions with anyone who
can read the repo. That's fine for plugins, but if you ever extend
the schema downstream to carry env-var hints or paths to private
plugin sources, add `_repo.yaml` to `.gitignore` or use env-var
references for secrets.

**Multi-worktree, same repo.** Same mode in two worktrees: fine,
fully isolated by branch. Different mode in two worktrees of the
same repo: also fine; SessionStart reconciles the cascade for the
current worktree (R27). A divergence toast appears when you switch
worktrees and the cascade output is being rewritten.

## Adoption story

"Set modes to shape which plugins are loaded; restart Claude Code to
change hooks, env, or permissions." Honest, narrow, ships.

Once a mode is feeling right, run `/mode:registry --rebuild` to
refresh the registry that backs `/mode:status` and the
slug-completion in `/mode:set`. The registry is a per-machine derived
artifact — never check it into source.

commands/                                   # /mode:set, /mode:clear, /mode:setup, etc.
lib/                                        # shell + Python: cascade engine, validators
scripts/                                    # hook shims, setup, uninstall, statusline
examples/                                   # example YAMLs (_global, _repo, delivery, discovery)
tests/                                      # unit + integration; tests/run.sh entrypoint
docs/                                       # brainstorms, plans, architecture, solutions
